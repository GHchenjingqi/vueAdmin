## 六、计划外增量收口：弃购召回邮件真正投递（15:00~15:20）

`16b1cc6` 在 P0~P10 闭环后补齐一个**功能性缺口**：弃购召回 / 收藏降价提醒邮件此前只入队、从未真正发送。

### 根因

弃购召回扫描器（`abandonedCartService.startAbandonedCartScanner`）和降价提醒（`wishlistService`）都把邮件写入
`shop_mail_outbox` 表（`ShopMailOutbox`），但仓库里**没有任何投递处理器**消费该表的 pending 行：
- 订单邮件（`orderMailService.drainOutbox`）走的是另一张表 `shop_order_email_outbox`（`ShopOrderEmail`）；
- 两表字段不同构（`ShopMailOutbox` 无 `attempts` CAS / `nextAttemptAt`），不能直接复用 `drainOutbox`。

结果：邮件永远停留在 `status='pending'`，顾客收不到任何提醒。

### 处理

| 缺口 | 处理 |
|---|---|
| 无投递扫描器 | 新增 `storefront/services/mailOutboxService.ts`：`drainMailOutbox`（单租户，status CAS 抢占 pending→sent，失败回退 failed 记 error）+ `scanAllTenantsMailOutbox`（按 pending 行 tenantId 分组逐租户 drain）+ `startMailOutboxScanner`（默认每 60s，进程级） |
| 抢占中间态 | `ShopMailOutbox.status` ENUM 仅 `pending/sent/failed`（无 `sending`）：改为「先 CAS 抢占到 sent 作锁，发送失败再回退 failed 并清 `sentAt`」 |
| 发送器复用 | `orderMailService` 新增导出 `getMailProvider()`（返回 `mailProvider ?? defaultProvider`），让营销 outbox 复用同一注入点（测试 `setMailProvider` 打桩一致） |
| 未挂载到进程 | `app.ts` 在弃购召回扫描器之后追加 `startMailOutboxScanner(60 * 1000)` |
| 零单测 | 新增 `mailOutboxService.test.ts` 3 例：pending 发送成功标 sent、失败回退 failed 记 error、非 pending 行跳过。3/3 通过 |

### 打扰规避（沿用上游）

收件人在入队前已由 `wishlistService` / `abandonedCartService` 过滤：未订阅营销邮件、无 email、blocked 状态均不入队。
扫描器本身只负责把 pending 尽力发出，失败不自动重投（外部邮件不可回滚，避免重复打扰；运营可在 admin 重发）。
