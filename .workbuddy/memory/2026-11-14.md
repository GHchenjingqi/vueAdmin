## 第十一轮缺陷审查（08:48+）— 计费/订阅"计息"路径审计

### 背景
用户说"计息"，代码库无字面利息/利率模块；最接近"按时间计费"的是 `server/modules/billing`
（订阅/账期/配额）。审计该模块并修复真实缺陷。

### 已确认并修复的真实缺陷
1. **订阅过期后仍无限期免费授予配额（计费失效 / 限额绕过，P1）**
   - `usageService.getLimit` 此前按 `status != 'cancelled'` 取最新订阅授予配额，**未校验 `currentPeriodEnd`**。
   - 全库**无任何订阅续费/状态翻转定时任务**（已 grep 确认：仅 `membershipService` 有会员定时任务，
     与计费订阅无关），订阅 30 天到期后 `status` 永久停在 `active`，导致配额被无限期免费授予。
   - 修复：`getLimit` 改为仅对 `status='active' AND currentPeriodEnd >= now` 的有效订阅授予配额。
   - 顺带：`GET /billing/subscription` 与配额闸门口径对齐（仅返回账期内 active 订阅）。
2. **`POST /billing/subscribe` 并发重复订阅（数据完整性，P2）**
   - 先查后改非原子，并发请求会各查到同一旧订阅、各自取消并创建 → 多个 active 订阅。
   - 修复：事务内对旧订阅加行锁（`SELECT FOR UPDATE`）后取消并创建新订阅，杜绝竞态。

### 已排除（非缺陷）

- Invoice/Payment 模型字段齐备，但计费链路未实际串联（功能缺口，非安全/计算缺陷）。

## 第 14 轮：账户/结账/RMA 核查 + 工作流审批回调未鉴权（CWE-306/345）

### 经核验为干净的面（无真实可利用缺陷）
- 账户安全：平台 `authService.changePassword` 校验原密码；顾客端独立 JWT（secret 隔离 + type 校验）、登录失败限流、httpOnly+SameSite=Lax Cookie、注销需密码二次确认；JWT 默认密钥在生产由启动守卫拦截（与 CORS/cookie/密钥守卫一致地依赖 NODE_ENV，不重复加固以免与既有设计冲突）。
- CORS/CSRF：显式白名单（credentials:true 仅对匹配 origin）、originValidator 拒绝跨站写、SameSite=Lax。
- referral/membership/coupon：storefront 侧仅只读（GET /me、/validate、/available），无自荐刷单/积分通胀/领用写端点暴露。
- RMA/退款：提交服务端按快照单价重算 + 事务内 LOCK.UPDATE + 累计已申请量防超额并发；退款核心 `refundService.ts:178-183` 强制 amountCents 永不超过 remaining（已付−已退）且关联 RMA 时不超过 rmaRefundCents → 超额退款被两端拦截。
- 结账：金额由 createQuote 服务端重算（不信任前端）、idempotencyKey 幂等、库存预占 TTL 失败释放；listMyOrders 按 JWT 归属、getOrder 需 accessToken 防枚举；自荐佣金 `referrer.id !== customerId` 拦截。
- 库存：`inventoryService.occupy` 同事务行锁 + 可用量校验（available=Σ(quantity−locked)，不足即抛错，固定加锁顺序防死锁）→ 无超卖竞态。
- SQL 注入：用户侧原始 query 均用 replacements 参数化（searchService/marketingService/refundService/couponService/addressService），无注入。
- 管理员路由：shop 路由几乎全部挂 authMiddleware，仅 `/health`（只读）与 `/workflow-callback`（见下，本次修复）例外。

## 第 15 轮：修复售后回补库存 + 退款恢复券用量（用户确认"可以修复"）

### 确证并修复的两大功能缺陷
- **缺陷1：RMA 退货/退款与换货不回补库存（账实不符）**
  - 证据：rmaAdminService.approveRmaWithRefund 驱动 RMA→refunded、approveRmaAsExchange 驱动→exchange，全程无 inventoryService.adjust 调用；订单取消/发货均会回补/扣减，售后端设计自相矛盾；rmaAdminService.ts:60 自承"售后与退款无调用关系、存在功能缺口"。
  - 修复（commit 9193675，已推送）：
    * inventoryService.adjust 增加可选 `transaction`/`ref` 参数；新增 `restockReturn(skuId,qty,ref,transaction?)`：优先回补至该 SKU 现有库存最多仓（最可能是原发货仓），无库存行时回退默认仓 1。
    * refundService 在驱动 RMA→refunded 的同事务内按 items 回补库存；用 `UPDATE ... affected` 守卫保证**恰好一次**（并发/幂等重放命中 0 行 → 不重复回补）。
    * rmaAdminService.approveRmaAsExchange 回补旧物库存（换货重发由后台新建发货 deduct，避免每笔换货净少一件）；回补失败隔离告警不阻断换货审批。
- **缺陷2：退款不恢复优惠券用量（与取消订单不对称）**
  - 证据：refundService 全文无 releaseCoupon 调用，而 orderService.cancel 会调用；退款后原订单占用券无法复用。
  - 修复：refundService 在**全额退款**（paymentStatus→refunded）后调用 `releaseCoupon(orderNo)` 恢复券用量；幂等（DELETE+条件递减）；失败隔离不阻断退款。部分退款不恢复（顾客保留部分购买）。
