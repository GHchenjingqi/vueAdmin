# storefront-ops-audit Insight · 独立站运营视角的改造优先级

Route: C（File-only）
依据：`storefront-ops-audit_dim01` ~ `dim06`、`_cross_verification.md`

## 一句话结论

这个项目**功能造得比它接得上的多**。后端已具备的能力（关键词检索、同义词、分区运费、税率 fail-closed、促销模型、到货订阅、UTM 落库、评价汇总）在 C 端链路上有相当一部分没有被接线，导致运营看到的"缺功能"多数其实是"功能没接上"。因此改造重点不是继续加模块，而是**补齐接线 + 锁定契约 + 让配置真正生效**。

这个判断改变了优先级排序：如果按"缺什么做什么"的思路，会重复建设已有能力；按"接线优先"的思路，投入最小、见效最快。

## 五个层次的判断

### 第一层：会直接损失钱或合规的（必须先修）

1. **BFF 丢参导致券/税/运费失效**（Dim01）。这是全项目影响面最广的单点缺陷：一处转发漏字段，三个收入相关机制同时失效。而且它有隐蔽性——页面不报错、订单能下、金额看起来"合理"（只是少了税和运费）。
2. **`commerceSource=auto` 静默回退 mock**（Dim06）。生产环境后端抖动时，顾客会看到演示商品并成功下单，订单落到 mock store。这类故障不会触发任何告警，属于最危险的一种。

这两项不需要新功能、不需要新表，都是小改动，但直接决定"账对不对"。

### 第二层：决定流量能不能变成订单的（发现层）

3. **搜索退化为前 24 条的前端过滤**（Dim02）。付费流量落地到搜索页时，长尾词全部丢失。后端 `expandTerm` 的同义词能力完全没被用上。
4. **类目 URL 是 `c-<id>`，类目 TDK 全部落空**（Dim02/Dim05）。类目页是独立站自然流量主入口，`SEO_SPEC.md` 写了 `/c/lace-wigs`，实际输出 `/c/c-11`。
5. **PDP 不渲染多图**（Dim02）。假发品类靠发际线、发缝、密度决策，单图不足以支撑客单价。

这三项的共同点：数据都在，只是没渲染/没透传/没消费。

### 第三层：决定每单人力成本的（履约层）

6. **无批量发货**（Dim04）。跨境日出百单时，逐单复制运单号是纯粹的重复劳动。
7. **商品无重量字段**（Dim03）。没有重量就无法按重计费、无法和货代账单对账、无法支撑多 SKU 混合订单的运费计算。
8. **RMA 批准不触发退款**（Dim04）。售后要人工在另一个界面再操作一次，且不支持部分退与换货。

### 第四层：决定投放能不能优化的（归因层）

9. **UTM 落库但报表无 utm 维度**（Dim03）。广告花费和订单收入之间没有可 join 的报表维度，ROI 只能人工拼 Excel。
10. **利润报表用申报价值当成本**（Dim03）。这是口径错误，会让"看起来赚钱"掩盖实际亏损，尤其在汇率波动时。
11. **促销活动不参与报价**（Dim03）。后台建活动、前台无变化，运营会逐渐弃用该模块。

### 第五层：决定长期信任与合规的（治理层）

12. **政策页写死在前端 mock**（Dim04）。合规文案更新要发版。
13. **营销邮件无 CTA、无退订**（Dim04）。转化率低，且有 CAN-SPAM / GDPR 风险。
14. **顾客 token 存 localStorage、无账号注销**（Dim04/Dim06）。安全基线低于后台管理端。
15. **品牌名写死，多站点能力未启用**（Dim05）。`siteContext` 支持 `X-Site-Id`，但 C 端从未发送。

## 一个反直觉的判断

**不建议现在做"更多功能"，建议先做"契约测试"。**

理由：Dim01 的丢参问题不是孤例——Dim02 的 keyword 未透传、Dim03 的 utm 未进报表、Dim04 的 restock 无入口，都属于同一类故障模式：**后端能力已实现，BFF/composable/页面三层中有一层没接上，且没有任何测试会发现它**。

单修 Dim01 只是修了一个症状。真正的解法是在 BFF 转发层加一条契约断言：前端请求体字段集合必须 ⊆ BFF 转发字段集合，缺一个就测试失败。这条测试写一次，能防住后续所有同类问题。

同理，后端的 `quoteSchema` 已经声明了 `shippingAddress` / `couponCode` / `pointsToRedeem`，但没有任何测试验证"从结算页发起报价时，这三个字段真的到达了 service"。补一条端到端契约测试，比再写三个功能更有价值。

## 建议的落地顺序（按投入产出比）

| 批次 | 内容 | 理由 |
| --- | --- | --- |
| 第 1 批 | BFF 报价/下单补全字段 + 生产强制 real + 契约测试 | 最小改动，直接修收入与数据真实性 |
| 第 2 批 | 搜索透传 keyword + 类目 slug 落库与回填 + PDP 多图 | 数据已有，改渲染与透传，直接提升转化 |
| 第 3 批 | 促销接入报价 + utm 报表 + 成本字段独立 | 让运营的投放与促销动作可衡量 |
| 第 4 批 | 批量发货 + 重量字段 + RMA 退款打通 | 降人力成本，支撑规模化 |
| 第 5 批 | 政策页 CMS 化 + 邮件模板升级 + 账号注销 + 品牌配置化 | 合规与长期信任 |

## 需要业务侧确认的前置项

以下几项不是代码能决定的，需要运营/财务确认后才能定实现：

1. **运费策略**：是按国家分区固定价，还是按重量阶梯？这决定 `ShopSku` 要不要加重量、运价表结构怎么设计。
2. **税务责任**：美国销售税是商家代收代缴（marketplace facilitator）还是 DDU 由买家承担？`MARKET_STRATEGY.md` 写的是 DDU + 商家代收销售税，两者并存需要在结算页明确告知。
3. **成本口径**：采购成本由谁维护、多久更新一次？这决定利润报表的可信度。
4. **促销优先级**：促销、券、会员折扣、积分同时命中时，叠加顺序是什么？必须先定规则再写代码，否则会出现"折上折到 0 元"。

## 方法边界

- 全部结论基于源码静态核对，未启动服务做运行时复现。
- "某功能不存在"的判断来自全目录关键词检索 + 路由清单比对，不排除以非预期命名实现。
- 支付网关的真实沙箱行为、数据库现存数据量对分页的影响，均未验证。
- 转化率影响（如 Apple Pay、评分富摘要）属行业经验判断，非本项目实测数据。
