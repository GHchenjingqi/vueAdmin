# vue-admin 商业化升级 · 执行计划总览

> 本目录是一组分步骤、可执行的落地计划文档，供 AI 编程助手（或开发者）**按编号顺序依次执行**。每个文件对应一个里程碑（M0–M6），完成一个里程碑再进入下一个。

---

## 一、商业化目标

将现有的「单组织内部后台管理系统」升级为「多租户可付费 SaaS / 可私有化交付」的商业化系统。

三条不可逆架构决策（已定，后续文档不再讨论）：

| 决策 | 选择 | 理由 |
|------|------|------|
| 多租户隔离 | 共享库 + `tenant_id` 行级隔离（默认），大客户可选库 per 租户 | 复用现有 `server/utils/dataScope.ts` 的 WHERE 注入模式，成本最低 |
| 服务边界 | 模块化单体（非微服务） | 已有 `server/modules/` 雏形，先内聚再按需拆 |
| 认证扩展 | JWT payload 携带 `tenantId` + 多策略可插拔 | 在 `server/middleware/auth.ts` 解码处扩展，SSO 作为身份源插件 |

## 三、通用执行约定（每个文档都遵守）

### 3.1 路径与基线
- 所有文件路径默认相对仓库根 `D:\codes\web\`（即 `server/...`、`src/...`）。
- 编码规范、命名风格、组件结构遵循 `AI_DEVELOPMENT_GUIDE.md`，**不引入新框架/库**，除非本计划显式列出依赖。
- TypeScript strict 模式，无分号、单引号、2 空格缩进（见 `.prettierrc`）。
- 源文件 UTF-8 无 BOM。

### 3.2 数据库迁移规范
- 引擎：Umzug（`server/utils/migrator.ts`）。
- 文件位置：`server/migrations/`。
- 命名：`YYYYMMDD_NNNNNN_描述.ts`（NNNNNN 为当日序号），如 `20260901_000002_add-tenant-id-to-business-tables.ts`。
- 新增迁移后用 `npm run migrate:status` 验证 executed。

### 3.3 模块化目录约定
商业化能力内聚进 `server/modules/<模块名>/`，每个模块自含：
```
server/modules/<module>/
├── models/         # Sequelize 模型
├── migrations/     # 不放这里，迁移仍统一进 server/migrations/
├── routes/         # 路由
├── services/       # 业务逻辑
├── middleware/     # 模块级中间件
└── index.ts        # 模块导出
```
迁移文件仍统一放 `server/migrations/`，但命名前缀体现模块。

### 3.4 验证命令（每个文档完成后必跑）
```bash
npm run typecheck     # 类型检查必须通过
npm run lint          # ESLint 无 error
npm test              # 单元测试全绿（新增测试随同提交）
npm run migrate:status # 迁移已 executed
```
后端单独：`cd server && npx vitest run`。前端：`npx vitest run`。

### 3.5 安全红线
- 绝不在代码或文档中写真实密码 / JWT secret。
- 多租户隔离：**任何业务查询拿不到 `tenantId` 时返回空集（where id=-1 兜底）**，平台超管显式 `bypass` 才放行。
- 新增对外接口必须经 `originValidator` 与鉴权中间件。
- 不提交 `.env`；密钥支持轮转。

### 3.6 文档内引用约定
- 计划中引用现有代码用 `文件路径:行号`，便于助手定位，如 `server/utils/dataScope.ts:121`。
- 每个"步骤"给出：新增/修改文件清单 → 关键代码骨架 → 验证点 → Definition of Done。

## 四、给 AI 助手的执行指令

1. **严格按文件编号顺序执行**，不要跳读 M5 而先做 M5。
2. 每完成一个里程碑文件的全部步骤，跑 3.4 的验证命令，全绿后方可标记该里程碑完成并进入下一个。
3. 若某步骤与现有代码冲突，**先读现有文件再改**，遵循 `AI_DEVELOPMENT_GUIDE.md` 14.1 的"先读后改、最小修改"原则。
4. 不要一次性把所有里程碑代码写完——逐个里程碑交付、验证、再继续，控制变更范围。
5. 每个里程碑文件结尾的 **Definition of Done** 是该里程碑的验收清单，逐条勾选。
